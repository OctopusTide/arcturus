# 权限名单与资源模块（第 5、6 件）

实现：`crates/daemon/src/modules/permission/`、`resource/`；Windows 系统操作在 `crates/platform/src/windows/resource.rs`。页面本身仍属于第 10 件，下面已经提供供页面调用的接口。

## 权限名单

只记录“不能关”，未列出的程序默认可以由资源策略处理。`permission.list` 返回完整路径、签名组织、来源、是否启用、是否不可删除，以及受保护任务与依赖的当前进程号。

- `builtin`：发现的 Windows 系统程序、安全软件、我们自己的程序。Windows/安全软件项要求完整路径不可被普通用户替换，并验证对应厂商签名；单靠文件名或位于 Windows\\Temp 不再成为内置项。不能删除。系统目录里的终端、记事本等按可删除的默认项处理。
- `default`：首次发现正在运行的 Claude、Codex、终端、VS Code、Office 等时，记录实际完整路径；有可验证签名时同时记录签名组织。用户删除后保留禁用记录，重启或再次发现不会加回来。
- `user`：用户自己添加的完整路径。
- 受保护任务及依赖在保护期间自动豁免；资源检查会继续找刚启动的子进程和依赖，不只依赖异步事件。
- 路径统一大小写与分隔符，拒绝相对路径、通配符、父目录跳转、设备路径和备用数据流。相同文件名在别的位置不算匹配。支持屏保 `.scr` 身份；个别不支持的发现路径不会让整张名单失效。卸载后的程序仍可移出用户名单。
- 签名验证支持内嵌签名与 Windows catalog，使用本地缓存，不请求外网检查吊销。身份、归属用户或签名无法核实时，资源操作保守跳过。

| 命令 | 参数 | agent 可调 |
|---|---|---|
| `permission.list` | 无 | 是 |
| `permission.set` | `program` 完整路径；`class`: `never` 加入、`may_end` 移出 | 否 |
| `permission.request` | 上述两项及非空 `reason` | 是 |
| `permission.requests` | 无，列待审批项 | 是 |
| `permission.review` | `request_id`、`approve` 布尔值 | 否 |

申请落库但立即无效，必须由可信页面批准；内置项即便走批准也不能删除。重复审批返回 `NOT_FOUND`。框架按系统报告的客户端路径识别页面，agent 自报身份没有作用。同账号下能绕开接口的限制仍见架构文档的“权限边界”。

## 资源策略

普通模式只发 `resource.notice` 并列出占用较大的候选程序，不冻结或结束程序。离开模式，以及启用 `free_memory` 的自定义模式，按整棵树的内存从大到小处理，微信最后。

默认每 5 秒检查：可用内存低于 10% 就冻结一棵完整进程树；30 秒后仍不足才结束已冻结的树。冻结后调用 `EmptyWorkingSet`，只是尽量移出物理页，提交额度不会因此释放。可用内存已足够时不强杀，冻结保留到回来。含豁免成员或无法读取成员的树整体跳过；管理员进程操作被拒时回滚并尝试其他候选，不绕过权限。

`back`、关闭自定义方案的内存处理、正常停止后台都会解冻资源模块持有的程序。新加入白名单或任务保护的已冻结树也会解冻。解冻失败的记录保留并重试，电源模块继续恢复，避免一个失败项永久挂住电源恢复；其他模块持有的冻结由各模块自己管理。

任务及依赖、名单或模式的变更与资源操作通过 `ModuleCtx::arbitration()` 同步串行化；事件负责唤醒与报告，不能用尚未送达的事件判断安全。名单或任务模块未就绪时停止自动操作。

受保护任务（包括新启动子进程）的内存超过 `mem_limit_mb` 时，停止继续腾内存并通知，避免任务泄漏拖累整台机器。

### 命令与设置

```text
away-guard free --mb 8192 --json
away-guard resource result --request-id 1 --json
away-guard resource check --json
away-guard resource settings --json
```

`free` 的 `mb` 是希望新增的可用 MB；省略时只申请达到压力阈值。立刻返回 `request_id`、`requested_mb`、`before_mb`、`target_mb`、`freed_mb`、`state`。`freed_mb` 是实际观察到的可用内存增量，不是进程占用估算；其他程序同时申请/释放内存也会影响它。

请求最多等待 5 分钟，目标不超过物理内存；过期状态为 `expired`，不再持续驱动冻结/强杀。过热处理仅选择低于普通优先级的候选树，降温且无内存压力时解冻热保护冻结的树。

状态：`pending` 等待后续检查；`completed` 达标；`needs_user` 普通模式或已回来；`task_limit` 任务自身超限；`insufficient` 没有可处理程序；`blocked` 安全状态未就绪或系统拒绝操作。通过 `resource.result` 查询后续结果；请求只在本次后台生命周期保留，最多 100 条，满时先移除已结束的请求。

`resource.configure` 只给页面，`settings` 部分更新：

| 设置 | 默认 | 允许范围 |
|---|---|---|
| `check_seconds` | 5 | 1–300 |
| `available_percent` | 10 | 1–90 |
| `freeze_wait_seconds` | 30 | 1–3600 |
| `video_limit_mb` | `null`，关闭 | 正整数或 `null` |

显存读取 GPU Adapter/Process Memory 的 dedicated usage；没有计数器时明确报告错误，不伪造零。默认只显示，开启上限后仅在允许自动处理的模式结束未受保护、占显存的进程树。普通模式超限只通知。显存没有冻结后等待策略。

### 恢复与验证

每次冻结前将进程号、创建时间、完整路径、各线程编号/创建时间/原暂停计数写入恢复日志，再暂停线程。线程列表或整棵树变化时回滚，后续检查重试。解冻只撤回本模块的一次暂停；检测到别的工具叠加暂停时保留恢复记录，等待重试。进程号或线程号已被复用则不碰新对象。路径不可读或不一致、但创建时间仍匹配时保留恢复记录，不误报已退出/已恢复，待身份重新可核实时再重试。安全读取暂停计数用 `NtQueryInformationThread`；系统不支持时拒绝冻结。终止操作有事前日志并明确不可撤销。

崩溃后下次启动解冻，即使资源模块在配置里已关闭，也执行恢复。不会因为恢复旧的结束进程记录而再结束任何程序。

验证：权限与资源共 16 个模拟集成测试，以及 2 个 Windows 实测（仅测试自行创建的 `ping`，另读取系统签名与显存）。工作区回归通过；没有对用户正在运行的软件执行冻结/强杀，没有安装自启或服务。真实应用在内存压力下的恢复体验仍需用户后续实测。
